# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

GranitDb is a metadata catalog for databases: it stores descriptions (databases, tables, columns, relations) in a catalog database and exposes them through a REST API and a Blazor WebAssembly UI. **No database server is required**: the catalog defaults to a SQLite file and a database to document can be a plain SQLite file. See `README.md` for configuration and `work-doc/` for the project assessment and the roadmap.

Projects (.NET 10; `GranitDb.sln` at the root holds them all, `api/` and `client/` also keep their own `.sln`):
- `api/` (`GranitDB.API`) — ASP.NET Core Web API (controllers, Swagger in Development, Dockerfile).
- `client/` (`GranitDb.Client`) — Blazor WASM + MudBlazor, PWA service worker.
- `tests/GranitDb.Tests` — xUnit; no external service needed.

## Commands

```bash
dotnet run --project api --launch-profile http    # http://localhost:5105, swagger at /swagger
dotnet run --project client                       # http://localhost:41248 (API URL: client/wwwroot/appsettings*.json)
dotnet test tests/GranitDb.Tests                  # all tests
dotnet test tests/GranitDb.Tests --filter "FullyQualifiedName~SchemaSynchronizerTests"   # one class
```

Target framework: .NET 10 (SDK 10 or newer).

## Architecture

**Catalog access.** `ICatalogRepository` (`api/Data/`) is the only way to read/write the catalog: generic Dapper CRUD driven by `[Table]`/`[NotMapped]` on the models in `api/Models/Descriptions/`, `FindAsync` filters in SQL on a whitelisted property, and `DeleteAsync` cascades manually (database → tables → columns → relations). `InTransactionAsync` hands back a repository bound to one connection/transaction (nestable): the synchronizer and every import run inside it, so they are atomic and fast (one commit instead of one per row) — never loop over single repository calls outside a transaction. `IDbConnectionFactory` opens SQLite (foreign keys enforced via PRAGMA) or SQL Server connections per `Catalog:Provider`.

**Migrations.** The catalog schema is versioned in `CatalogMigrations` (one SQL list per provider, never edit a published migration — append one). `MigrationRunner` applies pending ones at startup (each in its own transaction, version recorded in `SchemaVersion`, concurrent starters tolerated, a catalog newer than the app is refused). `SqlServerBootstrap` waits for the server (up to ~60 s) and creates the database. `InitV1.sql` is only a reference of the final SQL Server schema.

**Sources and sync.** `ISchemaConnector` (`api/Connectors/`) reads a source's schema into a `SourceSchema` and never writes to it: `SqliteSchemaConnector` (read-only open, `pragma_table_xinfo` / `pragma_foreign_key_list`) and `SqlServerSchemaConnector`. `SchemaSynchronizer` merges a `SourceSchema` into the catalog: tables/columns/indexes are matched by name (SQL Server tables outside `dbo` are named `schema.table`), hand-written descriptions are preserved, vanished items are deleted, and foreign keys become `Relations` marked `MetaInfo = "auto:fk"` (recreated on each sync; manual relations are untouched). A relation's `FirstId` is the referenced column and `SecondId` the referencing column. **Multi-column relations (migration 12):** a composite foreign key is one relation: its first pair stays in `Relations.FirstId/SecondId`, the next ones are `RelationColumns` rows (`RelationColumnInfo`, position ≥ 1, no FK, cascades by hand in `DeleteAsync`), exposed as `RelationInfo.ExtraColumns` (`[NotMapped]`, filled by `GetRelationsOfDatabaseAsync` and `RelationInfoController.GetT`; `Pairs()` lists all). Connectors set `SourceForeignKey.Constraint` only for composite keys (all pairs share it, in key order); the synchronizer and `SchemaDiffer` group by it. `RelationInput.ExtraColumns` and `DocRelationInput.Extra` carry the other pairs (same table on each side).

**SQL Server sources.** Gated by `Catalog:AllowSqlServerSources` (default true, set false to forbid: the API must not connect to a server chosen by the caller; `GET Capabilities` tells the client). `SqlServerImportController` (`import/sqlserver/test|POST|PUT {id}`) builds the connection string with `SqlConnectionStringBuilder` from `SqlServerConnectionInput` (never string concatenation), reads the schema only (`ApplicationIntent=ReadOnly`), filters by chosen schemas (`SourceSchemaFilter`) and stores `{ConnectionString, Schemas}` as JSON encrypted by `ISecretProtector` (Data Protection, keys in `Catalog:KeysDirectory`, default `DataDirectory/keys`) in `Databases.SourceSecret` (migration 9, `[JsonIgnore]`) with a non-secret `SourceLabel`. `ReadSourceAsync` serves both resync and preview for SQLite and SQL Server; an undecryptable secret gives a "saisissez-la de nouveau" error, a database read only through `StartupSources` has no secret and cannot be resynced by the API. `SqlServerErrors.Describe` maps driver error numbers to instructions (test 4060 before 18456: an unknown database raises both) and a connection failure during `/test` is a 200 with `ok:false`, not a 400. **Output DTOs:** `DatabaseView` (no `SourcePath`, no secret, `CanResync`), `SyncSummaryView`, `ImportView` — never return `DatabaseInfo` or `SyncResult`/`ImportResult` directly (`BaseDbInfoController.View` is the hook). `ModifyAsync` takes the caller's identity (`Actor` = authenticated `User.Identity.Name`, null today) for `History.ChangedBy`; tests simulate a caller with the `X-Test-User` header (a test-only `IStartupFilter` in `KestrelApiFactory`).

**Domain display settings & deletions.** `DomainInfo.ShowNeighbors` (default false: the domain diagram draws only the domain's own tables, neighbours from other domains in dashed "frontier" nodes only when true) and `DomainHiddenRelations` (relations not drawn in that domain; no FK on the relation, cleaned by `DeleteAsync` cascades) arrive with migration 10 and are set through `PUT DomainInfo/{id}/settings` (absent fields untouched; `DomainInput.ShowNeighbors` is nullable so a rename keeps it). `DELETE DatabaseInfo/{id}` goes through `DatabaseImportService.DeleteDatabaseAsync` (cascade + a `Deleted` row in `History` via `RecordHistoryAsync` + removal of the kept source file); the client asks to retype the name (`DeleteDatabaseButton`). `POST import/sqlite/{id}/preview` diffs a replacement file without writing or keeping it. `POST import/documentation/{databaseId}` (`DocumentationImportController`) fills empty descriptions, domains (with an optional layout) and manual relations from an external documentation, matching by name (a domain may carry `drawnRelations`: the other relations between its tables are stored as hidden for that domain; `work-doc/herakles-tools/convert-dataedo.mjs` builds its JSON from a Dataedo HTML export; `work-doc/herakles/` is git-ignored).

**Audit and webhooks (migration 11).** `AuditMiddleware` (registered before the exception handler) writes one `AuditLog` row per write request and per `/export/` call (actor, method, path without `/api/v1`, status, controller, route id, IP; never the body); `GET Audit` filters/pages it. `Webhooks` stores subscriptions (secret encrypted with `ISecretProtector`, never returned); `DatabaseImportService.NotifySchemaChange` enqueues `schema.changed` on resync/replace/startup sync when tables, columns or indexes changed, and `WebhookDispatcher` (a `BackgroundService`) POSTs it with retries and an `X-GranitDb-Signature: sha256=` HMAC. Targets that are loopback/private are refused at registration and again at connection time (`WebhookUrlPolicy`, `ConnectCallback`) unless `Webhooks:AllowPrivateHosts`.

**Exports.** `GET DatabaseInfo/{id}/export/markdown|csv` (`DocumentationTextExporters`; CSV escapes leading `=+-@`) and `export/xlsx` (`XlsxExporter`: hand-written OOXML zip, sheets Tables/Colonnes/Relations/Index, inline strings never formulas) share `HtmlDocumentationExporter.LoadAsync`. `GET DatabaseInfo/{id}/export/html` (`HtmlDocumentationExporter`) returns one self-contained HTML file (data embedded as JSON, inline CSS/JS, hash router) styled like the Dataedo export in `work-doc/herakles` (blue side nav with domain/table tree, breadcrumb, summary, columns, relations, indexes, plus SVG ERDs drawn in the page script: one per domain from the saved plan minus hidden relations, one neighbourhood diagram per table); the single "Exporter" menu is on the database page (HTML, Markdown, CSV, Excel, PDF); PDF has no server renderer: the HTML export has a printable view (`#/print`, one table per page) that the menu opens in a tab for the browser's "save as PDF".

**OpenAPI contract and generated client.** Swagger (`AddSwaggerGen` in `Program.cs`) describes only `api/v1/` routes, every operation named `Controller_Action` (generic base actions lose their trailing `T`), and `Swagger/ResponseTypesFilter` declares each operation's response type (actions return `IActionResult`, so nothing else says what they answer; add new routes there). `client/api/openapi.json` is the committed contract; `OpenApiContractTests` fails when it no longer matches the API. After any API route/type change run `scripts/generate-client.ps1` (writes the contract via that test with `GRANITDB_UPDATE_OPENAPI=1`, then NSwag generates `client/api/Generated/GranitApiClient.cs` — one client per controller in `GranitDb.Client.Generated`, grouped by `GranitApi` — and `GranitApiContracts.cs` — the DTOs and client interfaces, in `GranitDb.Client.Models`). The UI's models are those generated DTOs (`DatabaseView`, `TableInfo`, `ColumnInfo`, `DomainView`, `ImportView`, `CapabilitiesView`, `SqlServerConnectionInput`…, lists are `List<T>`); `client/Models/CatalogModels.cs` only adds partial members (default values, `RelationInfo.Pairs()`, `SearchHit.Href`) and the UI-only types (`Page<T>`, `AuditFilter`, `WebhookForm`). Never edit the generated files. `client/api/Client.cs` is the UI's facade over the generated clients: same method names as before, errors turned into `ApiException`/`HttpRequestException`, optional reads falling back to empty values, header totals (`X-Total-Count`, `wrapResponseMethods` in the script) and file exports (raw `HttpClient`: the contract does not describe files as data). A generated client is strict about status codes (201 for creations, 204 for deletions, declared in `ResponseTypesFilter`): test doubles must answer like the API, and `ClientAgainstApiTests` runs the facade against the real API.

**Import.** `DatabaseImportService` handles SQLite uploads (`POST /import/sqlite`, `PUT /import/sqlite/{id}`, `POST /import/sqlite/local` behind `Catalog:AllowLocalPaths`) and `POST /DatabaseInfo/{id}/sync`. Uploaded files are checked (SQLite header, size), stored in `<DataDirectory>/sources/` under a server-generated GUID name, and only re-read from that folder unless local paths are allowed. `Catalog:StartupSources` syncs declared sources at startup.

**API surface.** Every controller is routed under `api/v1/` and, as a legacy alias, without prefix (two `[Route]` attributes; the client uses `api/v1`). `BaseDbInfoController<T, TInput>` gives GET all (optional `skip`/`take` paging with `X-Total-Count`, sorted by name, plus the query filters declared by each controller in `Filters`: parameter → property + `FilterMode` Equals/Contains/Bool, applied in SQL by `ICatalogRepository` through `CatalogFilter`) / GET id / POST / PUT / DELETE. POST/PUT bodies are `InfoInput<T>` DTOs (`api/Models/Inputs/`, DataAnnotations validated by `[ApiController]`), never the entity: server-managed fields (e.g. `DatabaseInfo.SourcePath`) are absent from them and a PUT goes through `ICatalogRepository.ModifyAsync` (read → `input.Apply` → update), which also appends every change of `Description`/`MetaInfo` to the `History` table (migration 7, no FK so it survives deletions; the synchronizer uses `UpdateAsync` and writes no history). `TableInfoController` overrides GET to include columns (by `Position`), indexes and relations, adds `GET TableInfo/database/{id}` (filters + paging) and `{id}/columns|indexes|relations`. `ImpactController` (`Impact/table/{id}`, `Impact/column/{id}`) walks the relations breadth-first with `ImpactAnalyzer` (dependents = who references me, dependencies = who I reference, within the element's database). `HistoryController` lists the history (tracked fields: `Description`, `MetaInfo`, `IsSensitive`). Every entity also has `PUT {id}/documentation` (description + MetaInfo only, via `ModifyAsync`); `ColumnInfoController` adds `PUT {id}/sensitivity`. `RelationInfoController` validates manual relations (columns exist, same database, no duplicate in either direction) and protects the `auto:fk` marker (`RelationInput.ResolveMetaInfo`); the synchronizer re-creates detected relations with their previous Id, type and description. Governance entities (`api/Models/Descriptions/GovernanceInfo.cs`, migration 8): `DomainInfo` + `DomainTableInfo` (table↔domain link carrying the remembered X/Y; `DomainInfoController` exposes `database/{id}`, `tables/{tableId}` with `?moveFrom=`, `layout`), `TagInfo` + `TagLinkInfo` (polymorphic link, type = database/table/column; `TagInfoController.attach`), all with their own Id so the generic repository works; `DeleteAsync` cascades their links manually, and `FilterMode.In` (`CatalogFilter.In`) backs the `domainId`/`tag` filters (`LinkFilters`). `CompletenessController` computes described/total per table (blank descriptions do not count; undescribed sensitive columns are counted apart). `SchemaDiffer` (used by `POST DatabaseInfo/{id}/sync/preview`) mirrors the synchronizer's matching rules without writing, and flags removals that would lose documentation — keep the two in step when changing either. `GranitExceptionHandler` maps `GranitExceptions` to 400 and DB constraint violations to 409 (ProblemDetails).

**Client.** The UI is a workspace: `Layout/MainLayout.razor` hosts `Explorer` (tree of databases → tables → columns with domains and favorites; roving tabindex, arrow keys via `granitdb.moveTreeFocus` in `index.html`), `TabStrip` (one tab per open page; tabs are buttons, not links, so a middle click does not also open a browser tab), `DetailPanel` (selection from the explorer), `CommandPalette` (Ctrl+K), `ToastHost`. Shared state lives in scoped services registered by `AddGranitWorkspace()` (`client/Workspace/`): `WorkspaceState` (tabs keyed by path — the query string does not make another tab —, favorites, selection, panels, persistence as JSON in `localStorage` `granitdb.workspace`; `CatalogChanged(databaseId, source)` tells every view to reread, the emitter passes itself as `source` to skip its own event; drawer open state set by the layout's breakpoint is **not** remembered, only user toggles — `SetExplorerOpen(open, remember)`), `Notifier` (toasts, success messages with an optional undo; errors stay inline next to what failed) and `CatalogCache`. Pages tell the workspace their tab title with `Workspace.Describe(Navigation.Uri, title)`. A table tab is `DatabaseDetail` on `/databases/{id}/tables/{table}` (`TableRoute`, optional `?column=` highlight), the database page being the same component without it. `InlineText` saves on blur/Enter, Escape cancels, and shows an undo toast unless `Silent`. Razor attribute values cannot contain escaped quotes (`\"`): use constants or helper methods. In bUnit, render components that need the workspace with `ShellTestBase` (fake API + services); `MainLayout` has its own `MudPopoverProvider`, so do not render another one next to it. `client/api/Client.cs` wraps `HttpClient` (registered in `Program.cs` from `ApiBaseUrl`): paged list (`X-Total-Count`), tables, upload, sync, global search. Pages: `Databases.razor` (paged list + drop zone), `DatabaseDetail.razor` (`?table=<id>` expands and scrolls to a table), `Search.razor` (`/search?q=`, results grouped by kind), `Manage.razor` (`/manage`: rename, colour and delete tags and domains), `Audit.razor` (`/audit`: filtered, paged audit log) and **Input dialogs** (`client/Components/Dialogs/`: `RelationDialog`, `DomainDialog`, `WebhookDialog`, `ConfirmDialog`, opened with `DialogHelper.ShowFormAsync/ShowDataAsync` from `IDialogService`; `MainLayout` hosts the `MudDialogProvider`, bUnit tests render their own and read dialog content from it, not from the page; popover/dialog content is never in the page's DOM) — they validate before sending, show server errors inline and close with Escape/Cancel without saving. `Webhooks.razor` (`/webhooks`: create/edit/test/delete, list deliveries; the API refuses a webhook with a plain-text 400, read by `Client.EnsureTextAsync`), `ConnectSqlServer.razor` (`/import/sqlserver[?id=]`: test then import, or replace the connection of database `id`; hidden behind `Capabilities`), `Diagram.razor` (`/databases/{id}/diagram`: domains panel, table picker, zoom, impact panel, SVG/PNG/Mermaid export; in a domain view the checkboxes mean membership, tables outside the domain but related to it are drawn as dashed *frontier* nodes (`ErNode.IsFrontier`, rows reduced to the related columns), node positions are saved per domain; dragging a table to a domain works both from the picker list (HTML5 drag-and-drop) and out of the SVG (`ErDiagramView.OnDragLeave` → page-level `_draggedTable` → `pointerup` on the domain card)). `DatabaseDetail.razor` edits in place through `Components/InlineText.razor` and `TagEditor.razor` (child components call the page through plain `Func`s, so the page must call `StateHasChanged()` itself after saving), uses `Components/NativeSelect.razor` for dropdowns (`MudNativeSelect` does not bind here), and shows the sync preview inline before applying (no dialog). The diagram is split in `Diagram/ErDiagram.cs` (pure model: layered auto-layout, edge routing, `ToSvg`, `ToMermaid`; nodes are mutable X/Y) and `Components/ErDiagramView.razor` (interactive SVG: drag, click = select; Razor reserves the `<text>` tag, so SVG text is built by hand in `Txt`; string parameters need `@` — `Param="@x"`, not `Param="x"`); downloads go through `granitdb.download|downloadPng|copyText` in `index.html`. `MainLayout.razor` holds the global search box (Enter navigates), the light/dark toggle (persisted in `localStorage` under `granitdb.theme`, system preference by default) and the breadcrumbs live in each page. Search is `GET /Search?q=` -> `ICatalogRepository.SearchAsync` (LIKE with `!` as escape character, per-kind limit). Client models are generated from the API contract (see above).

## Tests

SQL Server tests (`SqlServerTests`, via Testcontainers) are skipped when Docker is unavailable unless `GRANITDB_REQUIRE_SQLSERVER=1` (CI sets it); the first run pulls the SQL Server image (~1.5 GB). Docker: `docker compose up --build` (SQLite) or `docker compose --profile sqlserver up --build` (needs `.env`, see `.env.example`); both Dockerfiles use the repo root as build context.
bUnit tests use `BunitContext` by composition + `IAsyncLifetime` (MudBlazor services are async-disposable only), never by inheritance.

`KestrelApiFactory` runs the API on a real Kestrel port instead of the in-memory TestServer. Test catalogs live in temp directories (`TestCatalog`); call `SqliteConnection.ClearAllPools()` before deleting SQLite files on Windows.

## Conventions

- Code comments and user-facing messages are mostly in French.
- The default data directory is `granitdb-data` (not `data`: `Data/` is a code folder and Windows paths are case-insensitive).
- Git: do not add Claude as author or co-author in commits (user instruction); work on a feature branch, not `main`.
